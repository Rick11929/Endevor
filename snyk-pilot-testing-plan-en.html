1. Background & Objectives

We have decided to run an internal pilot of Snyk. Because the Snyk Broker service (required for connecting Snyk to our internal/private repositories behind the firewall) cannot be deployed in the corporate intranet in the short term, all Broker-dependent capabilities are deferred to Phase 2. This first pilot phase is therefore limited to Snyk CLI and IDE plugin workflows, which operate from the developer workstation and do not depend on the Broker.

In addition, this pilot covers three Snyk capabilities only: SAST (Snyk Code), SCA (Open Source), and IaC. Other Snyk products and capabilities — including Snyk Container, license compliance, and reporting/governance features — are not part of this pilot.

1.1 Objectives

  • Validate core value: confirm Snyk can accurately detect vulnerabilities (SCA), code issues (SAST), and misconfigurations (IaC) in our real internal codebases via CLI and IDE.
  • Evaluate developer experience: measure installation friction, scan speed, result readability, fix workflow, finding triage workflow, and false-positive burden in day-to-day development.
  • Verify internal-network compatibility: confirm CLI/IDE work within our corporate network (proxy, firewall, internal package registries such as Nexus/Artifactory, internal CA certificates).
  • Collect adoption signals: understand whether developers would keep using Snyk after the pilot, before we invest in Broker deployment and broader rollout.
  • Produce a go/no-go recommendation for Phase 2 (Broker deployment + SCM/CI integration) with concrete data.

3.1 Roles

  • Pilot Lead (1): owns plan execution, triages issues, interfaces with Snyk vendor/support.
  • Security Champion(s) (1–2): validates severity/false-positive assessments, owns the weekly triage review, defines baseline expectations.
  • Pilot Participants (40): execute assigned test cases, triage their findings, file feedback weekly.

3.2 Selection Criteria for Participants

  • Works on an actively maintained internal repository with real dependencies.
  • Mix of seniority levels (at least 25% junior/mid to surface usability friction).
  • Willing to commit ~1–2 hours/week for 4–6 weeks and complete weekly surveys.

4. Environment & Prerequisites

4.1 Accounts & Licensing

  • Snyk Organization created; pilot group(s) configured.
  • 40 seats provisioned; SSO (or invited accounts) enabled.
  • API tokens distributable to CLI users.
  • Confirm plan limits (test counts for Snyk Code / IaC) fit pilot volume.

4.2 Network

  • Firewall/proxy allowlist: snyk.io, api.snyk.io, app.snyk.io, deeproxy.snyk.io (Snyk Code), update endpoints.
  • Corporate root CA available for CLI/IDE (NODE_EXTRA_CA_CERTS or equivalent).
  • Proxy env vars documented for participants (HTTP_PROXY/HTTPS_PROXY).

4.3 Test Assets

  • 6–10 representative internal repos (varied languages/build tools: Maven/Gradle, npm/yarn/pnpm, pip/Poetry, Go modules).
  • At least 1 monorepo and 1 repo with multiple manifests.
  • 1 repo with known vulnerable dependency versions (seeded, non-production) for detection validation.
  • Terraform / Kubernetes YAML samples for IaC scanning.

4.4 Tooling Versions

  • Latest stable Snyk CLI (pin version at pilot start; record it).
  • VS Code Snyk extension (latest stable).
  • JetBrains Snyk plugin (IntelliJ IDEA / PyCharm / WebStorm).
  • OS mix: Windows + macOS (+ Linux if used by devs).

6.4 Finding Triage Workflow (SCA + SAST)

Triage = the end-to-end loop a developer/champion performs on a finding: review → prioritize → decide (fix / ignore / escalate) → act → verify. Since Jira/SCM integrations are out of scope, assignment is manual and tracked via the weekly triage review and the Snyk UI audit trail.

IDPriTest CaseExpected Result
TRI-01P0Review & prioritize: from CLI output and the Snyk UI (monitored projects), sort/filter findings by severity, Snyk Priority Score, exploit maturity, and fixability.Developer can produce a prioritized work queue in ≤ 5 min; priority metadata (CVSS, exploit maturity, "fix available") is visible and sufficient to make a decision.
TRI-02P0Triage decision loop: each participant takes ≥ 5 real findings on their repo and records a decision per finding: Fix now / Ignore with reason + expiry / Escalate to Security Champion.Every decision is recorded and traceable; median time-to-triage per finding ≤ 5 min (self-timed, reported in weekly survey).
TRI-03P1Ignore mechanics: suppress an accepted-risk finding via snyk ignore and/or a .snyk policy file (reason + expiry date); re-scan.Finding suppressed on re-scan; ignore visible in Snyk UI with reason/expiry (audit trail); expired ignores reappear (spot-check by setting short expiry).
TRI-04P1Fix & verify loop: fix a triaged finding (upgrade dependency / change code), re-scan in CLI and IDE, then re-run snyk monitor.Fixed finding clears in CLI, IDE, and web UI; no regression introduced; UI snapshot reflects the fix.
TRI-05P1Escalation path: escalate a disputed finding (suspected FP or unclear severity) to the Security Champion; champion reviews and either confirms, reclassifies, or reports to Snyk support.Escalation resolved within 3 business days; outcome documented in the issue log; vendor tickets filed where needed.
TRI-06P2Weekly triage review (team-level): Champion + Pilot Lead run a 30-min weekly review of new Critical/High findings across monitored projects in the Snyk UI.Burn-down of Critical/High findings is trackable week-over-week; ≥ 90% of new Critical/High findings have a documented triage decision by the next review.
TRI-07P2Triage UX pain points: collect feedback on what is missing without Jira/SCM integration (assignment, notifications, bulk actions).Gap list produced as Phase 2 requirements input (e.g., Jira integration, bulk ignore, SLA policies).

9.4 Collection Mechanisms

  • Case tracker (in snyk-pilot-scorecard.xlsx): every case gets a status (Pass / Fail / Blocked / N/A) + measured value + note; EX-1/EX-2 and the Section 10 verdicts compute automatically.
  • Weekly 5-minute survey (W1–W4): scans run, failures, blockers, triage decisions, time-to-triage (feeds M-3, M-8).
  • Issue log: every bug/blocker tagged by component (CLI/IDE/network/docs) and severity; escalations from TRI-05 tracked here (feeds M-12).
  • Triage audit trail: ignore reasons/expiry in .snyk files and the Snyk UI; weekly Critical/High burn-down from the Org UI (feeds M-9).
  • W4 mini-survey: 5 questions (Appendix B), entered into the scorecard workbook — averages and % Yes compute automatically (feeds F-1…F-5).
  • W5 debriefs: 30-min interviews with 8–10 participants; qualitative context for any FAIL verdict.

How to read failures (traceable by design): each failed criterion names its cases, so the pilot report can point at exactly what broke. Examples: SC-7 fail → finding quality problem, check CLI-21 FP list; SC-9 fail → triage loop problem, review TRI-02/TRI-06 notes; SC-5 fail → onboarding/docs problem, review CLI-01–04 blocker notes. P0-gate failures (detection, network, security sign-off) are vendor/architecture blockers and should trigger competitive re-evaluation before Phase 2 investment.

12. Exit Criteria & Next Phase

12.1 Pilot Exit Criteria

  • All test cases executed with status recorded in the scorecard workbook; issue log triaged to zero untriaged items.
  • Scorecard finalized: all Section 9 metrics populated; Section 10 verdicts computed.
  • Go/no-go recommendation presented to stakeholders with:
    • Success-criteria scorecard (Section 10) with case-level evidence,
    • Top issues & vendor support experience,
    • Triage-workflow gap list (TRI-07) — what Jira/SCM integration must provide in Phase 2,
    • Phase 2 requirements (Broker architecture, endpoint allowlist delta, SCM/CI integration plan, estimated effort).

12.2 Phase 2 Preview (Post-Broker)

  • Broker deployment is the gating dependency for Phase 2 — it cannot be set up in the corporate intranet in the short term; revisit the deployment timeline with the network/security teams and use Phase 1 network findings (XC-01) to pre-draft the Broker host, architecture, and allowlist requirements.
  • Once Broker is available: integrate internal GitLab/GitHub Enterprise for repo import & automated fix PRs.
  • CI gate design using validated exit-code/severity-threshold behavior from CLI-16.
  • Jira/Slack integration to close the triage gaps identified in TRI-07 (assignment, notifications, SLA tracking).
  • Policy & governance setup; expand to full engineering org based on Phase 1 scorecard results and debrief learnings.
  • Snyk Container and other Snyk capabilities remain out of scope and would require a separate evaluation if needed later.

B.2 Scoring

Rating (F-1/F-2/F-3) = (sum of 1–5 answers) ÷ (number of answers) → target ≥ 4.0
Yes/No (F-4/F-5) = (count of "Yes") ÷ (number of answers) × 100% → target per metric

Worked example: 38 of 40 participants respond. Q1 answers sum to 160 → F-1 = 160 ÷ 38 = 4.2 → PASS (≥ 4.0). Q4: 29 Yes of 38 → F-4 = 76% → PASS (≥ 70%). Both feed Section 10 verdicts directly (SC-10, SC-11).
