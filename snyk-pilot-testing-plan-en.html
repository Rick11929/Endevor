1. Background & Objectives

We have decided to run an internal pilot of Snyk. Because the Snyk Broker service (required for connecting Snyk to our internal/private repositories behind the firewall) cannot be deployed in the corporate intranet in the short term, all Broker-dependent capabilities are deferred to Phase 2. This first pilot phase is therefore limited to Snyk CLI and IDE plugin workflows, which operate from the developer workstation and do not depend on the Broker.

In addition, this pilot covers three Snyk capabilities only: SAST (Snyk Code), SCA (Open Source), and IaC. Other Snyk products and capabilities — including Snyk Container, license compliance, and reporting/governance features — are not part of this pilot.

Staffing constraint: this pilot has no dedicated Security Champion. The measurement model is therefore deliberately simple: testers run the test cases, then fill in one end-of-pilot questionnaire (Appendix A, 20 questions, mostly counts and Yes/No). Every success criterion in Section 10 is a formula over those answers, computed automatically in the scorecard workbook (snyk-pilot-scorecard-v3.xlsx). Objective anchors run by the Pilot Lead (a seeded vulnerable repo, a network checklist, a governance sign-off) cover the few criteria a questionnaire cannot measure.

1.1 Objectives

  • Validate core value: confirm Snyk can accurately detect vulnerabilities (SCA), code issues (SAST), and misconfigurations (IaC) in our real internal codebases via CLI and IDE.
  • Evaluate developer experience: measure installation friction, scan speed, result readability, fix workflow, finding triage workflow, and false-positive burden in day-to-day development.
  • Verify internal-network compatibility: confirm CLI/IDE work within our corporate network (proxy, firewall, internal package registries such as Nexus/Artifactory, internal CA certificates).
  • Collect adoption signals: understand whether developers would keep using Snyk after the pilot, before we invest in Broker deployment and broader rollout.
  • Produce a go/no-go recommendation for Phase 2 (Broker deployment + SCM/CI integration) with concrete data.

3.1 Roles (no Security Champion)

  • Pilot Lead (1): owns plan execution; runs the objective-anchor cases personally (CLI-11 seeded repo, XC-01 network matrix, XC-02 governance checklist, CLI-30 / IDE-20 timings); maintains the issue log; runs the weekly 30-min triage review (TRI-06); first escalation point for disputed findings (TRI-05); files Snyk vendor support tickets; distributes the questionnaire at the end of W4 and enters answers into the scorecard workbook.
  • Pilot Participants (40): execute assigned test cases, label their own Snyk Code findings TP/FP/Unsure using the rubric (CLI-21), triage their findings, jot down their counts as they go (a simple tally is enough), and fill in one end-of-pilot questionnaire (≤ 10 min, Appendix A).
  • Vendor support (Snyk): replaces expert judgment for disputes the Pilot Lead cannot resolve — any contested severity/FP call becomes a vendor ticket.
Why this works without a Security Champion: detection quality is anchored objectively by the seeded repo (CLI-11 — we know exactly what should be found); the false-positive rate is counted from tester self-labels using a strict rubric (CLI-21) rather than judged by an expert; disputed calls escalate to the Pilot Lead and then to the vendor. The trade-off (self-reported counts with end-of-pilot recall) and its mitigations are documented in Section 11.

3.2 Selection Criteria for Participants

  • Works on an actively maintained internal repository with real dependencies.
  • Mix of seniority levels (at least 25% junior/mid to surface usability friction).
  • Willing to commit ~1–2 hours/week for 4–6 weeks and complete the end-of-pilot questionnaire.

TP / FP / Unsure labeling rubric (used in CLI-21 and questionnaire Q7–Q9)

  • TP (true positive): the flagged pattern can actually occur in our code — e.g., user input really reaches the SQL query without sanitization; the vulnerable dependency function is really called.
  • FP (false positive): the flagged pattern cannot occur in our context — e.g., input is a constant/server-side config, the vulnerable code path is unreachable, the finding flags test/example code, or the recommended fix is already applied.
  • Unsure: cannot decide within ~2 minutes. Record as Unsure — do not guess. Reviewed with the Pilot Lead; still unresolved → Snyk vendor ticket.
  • Rule of thumb: if you would not change the code because of this finding, it is probably an FP — write down why.

9. Metrics — How the Questionnaire Produces Every Number

The measurement model, in one sentence: testers execute the test cases during W1–W4, then each tester fills in one end-of-pilot questionnaire (Appendix A — 20 questions, all counts / Yes-No / 1–5 ratings); the scorecard workbook turns those answers into every metric below and into the PASS/FAIL verdicts in Section 10. Nobody calculates anything by hand — each question maps to exactly one metric, and each metric maps to exactly one success criterion.

Worked example — the FP rate (M-6) straight from the questionnaire: Q7 asks "how many of your reviewed Snyk Code findings were True Positives", Q8 asks how many were False Positives, Q9 how many Unsure. Say the 40 questionnaires sum to ΣTP = 231, ΣFP = 58, ΣUnsure = 23. The workbook computes M-6 = 58 ÷ (231 + 58) = 20.1% → PASS (target ≤ 30%) → SC-7 passes. The 23 Unsure findings are never guessed — they went to the Pilot Lead during the pilot and became vendor tickets if unresolved. Same pattern for every other metric: question counts in, formula out, verdict automatic.

9.4 Collection Mechanics

  • Tally sheet during the pilot: at onboarding every tester gets a one-page tally sheet (scans run/failed, TP/FP/Unsure, fixes/cleared, new C/H + decided, triaged + minutes). Jotting a count takes seconds and makes the end-of-pilot questionnaire a copy-paste exercise instead of a memory test.
  • Questionnaire at end of W4: 20 questions, ≤ 10 minutes, numbers / Y-N / 1–5 only. Pilot Lead collects answers (form or email) and types them into the Questionnaire sheet — one row per tester. All metrics and verdicts compute automatically.
  • Spot-check: the Pilot Lead cross-checks 5 random testers' counts against the Snyk UI (monitored projects show scan and finding counts) and flags anomalies — keeps self-reported numbers honest without any expert review layer.
  • Issue log (Pilot Lead): every bug/blocker tagged by component and severity; Unsure FP labels and TRI-05 escalations land here and convert to vendor tickets after 3 business days (feeds M-12).
  • W5 debriefs: 30-min interviews with 8–10 participants; qualitative context for any FAIL verdict.

On the honesty of self-reported numbers: SC-7 relies on tester self-labeling, which is noisier than expert review. Three compensating controls keep it trustworthy: (1) the CLI-21 labeling rubric gives an objective decision rule for TP / FP / Unsure, and Unsure items are never silently dropped — they go to the Pilot Lead and then to the vendor; (2) the CLI-11 seeded repo (run by the Pilot Lead, ground truth known) acts as an objective anchor for detection quality, so a vendor quality problem cannot hide behind generous self-labeling — if Snyk misses seeded vulnerabilities, SC-2 fails regardless of what testers report; (3) the Pilot Lead spot-checks 5 random testers against Snyk UI counts. If SC-7 passes but W5 debriefs contradict it, the debrief evidence wins and SC-7 is treated as FAIL.

How to read failures (traceable by design): each failed criterion names its questions and cases, so the pilot report can point at exactly what broke. Examples: SC-7 fail → finding quality problem, review the Q8 (FP) answers and the Unsure items sent to the vendor; SC-9 fail → triage loop problem, review Q12–Q15 distributions and TRI-02/TRI-06 notes; SC-5 fail → onboarding/docs problem, review Q1–Q3 and the CLI-01–04 blocker notes. P0-gate failures (detection, network, security sign-off) are vendor/architecture blockers and should trigger competitive re-evaluation before Phase 2 investment.

12. Exit Criteria & Next Phase

12.1 Pilot Exit Criteria

  • All test cases executed with status recorded in the scorecard workbook; issue log triaged to zero untriaged items.
  • Questionnaire response rate ≥ 90% (≥ 36 of 40 testers); all Section 9 metrics computed; Section 10 verdicts finalized in the workbook.
  • Go/no-go recommendation presented to stakeholders with:
    • Success-criteria scorecard (Section 10) with question-level evidence,
    • Top issues & vendor support experience (incl. Unsure/escalation ticket outcomes),
    • Triage-workflow gap list (TRI-07) — what Jira/SCM integration must provide in Phase 2,
    • Phase 2 requirements (Broker architecture, endpoint allowlist delta, SCM/CI integration plan, estimated effort).

12.2 Phase 2 Preview (Post-Broker)

  • Broker deployment is the gating dependency for Phase 2 — it cannot be set up in the corporate intranet in the short term; revisit the deployment timeline with the network/security teams and use Phase 1 network findings (XC-01) to pre-draft the Broker host, architecture, and allowlist requirements.
  • Once Broker is available: integrate internal GitLab/GitHub Enterprise for repo import & automated fix PRs.
  • CI gate design using validated exit-code/severity-threshold behavior from CLI-16.
  • Jira/Slack integration to close the triage gaps identified in TRI-07 (assignment, notifications, SLA tracking).
  • Policy & governance setup; expand to full engineering org based on Phase 1 scorecard results and debrief learnings.
  • Snyk Container and other Snyk capabilities remain out of scope and would require a separate evaluation if needed later.

A.1 How the Score Is Computed (no manual math — the workbook does this)

M-1 = COUNT(Q1 = Y) ÷ 40 → SC-5 (target ≥ 90%)
M-2 = MEDIAN(Q2) → info (target ≤ 30 min)
M-3 = 1 − ΣQ5 ÷ ΣQ4 → SC-6 (target ≥ 95%)
M-6 = ΣQ8 ÷ (ΣQ7 + ΣQ8) → SC-7 (target ≤ 30%)
M-7 = ΣQ11 ÷ ΣQ10 → SC-8 (target ≥ 95%)
M-8 = ΣQ15 ÷ ΣQ14 → SC-9 (target ≤ 5 min, with M-9)
M-9 = ΣQ13 ÷ ΣQ12 → SC-9 (target ≥ 90%, with M-8)
M-13 = COUNT(Q16 = Y) → SC-3 (target 0, with M-12)
F-1/F-2/F-3 = AVERAGE(Q17 / Q18 / Q19) → SC-10 (target ≥ 4.0)
F-4 = COUNT(Q20 = Y) ÷ respondents → SC-11 (target ≥ 70%)
F-5 = COUNT(Q3 = Y) ÷ respondents → info (target ≥ 80%)

Final verdict: GO = all 4 P0 gates pass (case tracker, seeded repo, network, security sign-off) AND at least 5 of the 7 aggregate criteria above pass. The Dashboard sheet of snyk-pilot-scorecard-v3.xlsx shows the verdict automatically once the questionnaire rows are entered.
