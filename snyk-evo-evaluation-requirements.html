1 Purpose & Background

We are evaluating selected capabilities of the Snyk Evo product family (part of the Snyk AI Security Platform) as candidates for our application security / AI security toolchain. This focused evaluation covers the "Discover" loop (Evo AI-SPM), the secure-at-inception development layer (Evo ADS / Snyk Studio), and the platform experience that ties them together (orchestration, reporting, dashboards, API). It must produce an evidence-based Go/No-Go recommendation measured against the acceptance criteria in §6.

3 Test Environment & Assets

Repositories (provided by us)

R1: active service with heavy AI-assisted development (JS/TS + Python). R2: LLM-integrated agent application (tool calling, MCP usage, prompt handling). R3: legacy service with known vulnerability backlog. All sanitised; no production data. A manually compiled ground-truth inventory of AI components ships with the repos.

Developer environments

5–8 UK team machines covering Claude Code, Cursor, GitHub Copilot (VS Code), and at least one MCP-heavy setup (10+ MCP servers). Mix of macOS and Windows.

CI environment

One shared CI pipeline per repo (GitHub Actions or equivalent) for Policy Agent guardrail tests in monitor and enforce modes.

Test task corpus

We provide: (a) 20 scripted AI-generation tasks known to induce vulnerabilities (SQLi, XSS, path traversal, hardcoded credentials, insecure deserialisation); (b) 20 scripted policy violation/compliance cases; (c) the ground-truth AI component inventory for AI-BOM accuracy scoring.

Access: Evo AI-SPM and Evo ADS entitlements, plus platform/API access, will be provisioned via our Snyk account team before Day 1. The UK team must confirm actual entitlement coverage in week 1 and escalate any gap immediately.

4 Methodology & Test Scenarios

4.1 Phase A — Baseline, Discovery & Governance (Week 1–2) · C1

A-1 · Baseline scans

Run Snyk Code/SCA baselines on R1–R3; record findings, duration, and false-positive impressions as comparators for later claims.

A-2 · AI-SPM discovery

Enable Discovery Agent across R1–R3 plus developer machines; generate AI-BOMs (snyk aibom locally where SCM integration is not used). Compare against the ground-truth inventory. Measure completeness, phantom-entry rate, and time-to-inventory.

A-3 · Risk Intelligence Agent

Verify inventory enrichment: model risk taxonomy scoring, skills/MCP server risk analysis inside the AI-BOM, security metadata quality. Sample-check 20 entries for correctness.

A-4 · Policy Agent

Author three natural-language policies (e.g. "no unregistered models", "skills with externally hosted instructions require approval", "block high-severity reachable vulns in PR"). Verify translation into CI-enforceable guardrails; run monitor mode for ≥ 3 working days, then enforce mode; grade against the 20 scripted violation/compliance cases.

4.2 Phase B — Secure-at-Inception (Week 2–3) · C2

B-1 · Studio/ADS rollout

Install via the official installer script on hooks-capable ADEs (Claude Code, Cursor, Copilot, Codex CLI) and via manual mcp.json MCP-server registration elsewhere. Validate with a "scan my directory for security issues" prompt. Record install time and failure modes per machine.

B-2 · Generation-time scanning

Execute the 20 scripted AI-generation tasks. Record detection-at-generation rate, fix-suggestion quality, and rescan-until-clean behaviour.

B-3 · MCP profiles & overhead

Test lite / full / experimental MCP profiles; measure token/context overhead per profile and median added latency per AI-generation round.

B-4 · Rules-based enforcement

Deploy Secure-at-Inception rules (per the official Windsurf-guide pattern) to all ADEs; verify the rule file is honoured across at least two different ADE families.

4.3 Phase C — Platform, Reporting & DX (Week 3–4) · C3

C-1 · Orchestration

Drive one multi-agent workflow from a single natural-language prompt (e.g. "discover all AI assets in R2, assess risk, and produce an executive report"). Record steps requiring human intervention.

C-2 · Reporting & dashboards

Assess Reporting Agent output quality and customisability; evaluate dashboards for the three audiences: developer, AppSec engineer, executive. Time how long an executive-ready report takes to produce, including manual editing.

C-3 · API & enterprise fit

Verify programmatic export of findings and AI-BOM data via API; SSO/RBAC; audit logs; data-residency/GDPR posture for UK/EU data (document where scan data and code snippets are processed and retained).

C-4 · Developer experience survey

Structured questionnaire for all participating engineers: interruption cost, scan latency, alert quality, trust in results — scored 1–5 with free text.

6 Acceptance Criteria

Each criterion is graded PASS / PARTIAL / FAIL with evidence attached. "Ground truth" refers to the test corpus in §3. Thresholds are targets for a confident Go; PARTIAL triggers a documented risk discussion, not automatic rejection.

C1 · Evo AI-SPM

AC-1.1 Discovery completeness: ≥ 90% of ground-truth AI components (models, MCP servers, skills, agent frameworks) present in the generated AI-BOM across R1–R3; ≤ 10% phantom entries.
AC-1.2 Time-to-visibility: full inventory for the three repos achievable within 1 working day of enablement.
AC-1.3 Risk enrichment: ≥ 90% of the 20 sample-checked AI-BOM entries carry correct risk scoring/metadata (skills and MCP server risk analysis included).
AC-1.4 Policy Agent: all 3 natural-language policies translated to CI-executable guardrails; in enforce mode, ≥ 95% enforcement accuracy on the 20 scripted violation/compliance cases; monitor mode produces zero pipeline disruption.

C2 · Evo ADS / Snyk Studio

AC-2.1 Install success on 100% of pilot machines across both setup paths (installer script and manual MCP registration), each ≤ 30 min effort.
AC-2.2 Secure-at-inception: ≥ 85% of the 20 scripted vulnerable-generation tasks flagged at generation time; flagged issues include actionable remediation guidance; rescan-until-clean loop functions without manual intervention.
AC-2.3 Overhead: median added latency per AI-generation round ≤ 30 s; MCP lite profile measurably reduces token/context cost vs full (quantified in report).
AC-2.4 Rules portability: the same Secure-at-Inception rule set is honoured by ≥ 2 ADE families without per-ADE rewriting of the rule content.

C3 · Platform & Reporting

AC-3.1 Single-prompt multi-agent workflow completes end-to-end and produces an executive-grade report with ≤ 30 min of human editing.
AC-3.2 Dashboards serve all three audiences (developer / AppSec / executive) without exporting to third-party tools for routine questions; any gap recorded as a named limitation.
AC-3.3 SSO/RBAC and audit logging verified; API allows full programmatic export of findings and AI-BOM data; UK/EU data processing & retention documented and consistent with our GDPR obligations.
AC-3.4 DX survey: mean score ≥ 3.5/5 on "would keep this in my workflow"; top 3 friction points documented.

Overall Go/No-Go rule

Go recommendation requires: all three capability areas at PASS or justified PARTIAL, with no FAIL on AC-1.1, AC-2.2, or AC-3.3. All criteria in this reduced scope cover GA capabilities only; any dependency finding touching excluded capabilities (§2.2) is reported separately and does not gate this decision.

7 Logistics, Constraints & Governance

  • Timeline: 4 weeks from environment readiness; weekly Friday sync + interim findings log; Week 4 readout to stakeholders.
  • Team: 2 UK engineers, ~60% allocation; one named lead owning deliverables D1–D5.
  • Safety: no offensive testing in this engagement; do not enable COS, red teaming, or Agent Guard even if visible in the tenant — flag accidental entitlement to the sponsor.
  • Data protection: only sanitised repos and synthetic data; the team must document Snyk-side processing locations/retention (feeds AC-3.3) and flag any UK GDPR concern within 48 h.
  • Versioning: record exact product versions / build dates for every test; features observed in preview state must be labelled as such in the final report.
  • Commercial firewall: no pricing or contract discussions with Snyk; route any such approach back to the sponsor.
